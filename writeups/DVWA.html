For brute forcing, I tried using Hydra in the beginning, but it turned out to be a bad decision. Either my lack of experience or other factors led to about one hour of trying to fix a command, which did not work even in the end

hydra 10.0.2.15 -L user.txt -P pass.txt http-get-form "/DVWA/vulnerabilities/brute/:username=^USER^&password=^PASS^&Login=Login:Username and/or password incorrect.H=Cookie: PHPSESSID=3n0mhopq9dvv2i66udhgpeqnmi; security=low"

A simplified command, without the Cookie resulted in false positives, categorizing every entry as successful.

hydra 10.0.2.15 -L user.txt -P pass.txt http-get-form "/DVWA/vulnerabilities/brute/:username=^USER^&password=^PASS^&Login=Login:Username and/or password incorrect.
1 of 1 target successfully completed, 18 valid passwords found

That is why I decided to use Burp, which is more reliable for web login brute-forces anyways, according to some sources I have encounted while trying to fix the command above.

This required intercepting the request for wrong credentials (test & test) in my case, sending it to intruder where the username and password were set as variables and the Attack Type was set to Cluster Bomb, and adding a word list for each of those variables using the "payloads" section.

In the end, it was enough to sort the results by Length, as the correct pair had a different length compared to all the other tries.

To further visualize the result, I also used the "show response in browser" option, which proved that the attack worked as intended: "Welcome to the password protected area admin"

simple commands like whoami, ls -la etc. did not return anything, so I used Burp to try to understand what the request looks like

ip=10.0.2.15&Submit=Submit

nothing caught my eye here, but while looking at the Command Injection documentation from Owasp, I saw something interesting

Used normally, the output is simply the contents of the file requested:

$ ./catWrapper Story.txt
When last we left our heroes...

However, if we add a semicolon and another command to the end of this line, the command is executed by catWrapper with no complaint:

$ ./catWrapper "Story.txt; ls"
When last we left our heroes...
Story.txt               doubFree.c              nullpointer.c

I applied this to my scenario, and it did in fact work:

For the High level, input sanitization is done with more care:

$target = trim($_REQUEST['ip']);

// Set blacklist
$substitutions = array(
    '||' => '',
    '&'  => '',
    ';'  => '',
    '| ' => '',
    '-'  => '',
    '$'  => '',
    '('  => '',
    ')'  => '',
    '`'  => '',
);

as well as

// Remove any of the characters in the array (blacklist).
$target = str_replace(
    array_keys($substitutions),
    $substitutions,
    $target
);

However, on the first try, the command still seems to work?

Enter an IP address:
10.0.2.15|whoami

www-data

but why does it work?

Seems like all the other options will not work (10.0.2.15;whoami, 10.0.2.15&whoami etc.)

After looking at the blacklist, I noticed what seems to be the error:

'| ' => ''

there is a space after the "|" character

the trim() method does not seem to be enough to fix this issue

After looking up trim(), I found out that it only removed whitespaces from the beginning and end of the string

As for the line that actually deals with the "|" character, '| ' => '', this only transforms the | character into whitespace IF the | is followed by a space

In that scenario, the attack would not work:

10.0.2.15| whoami
